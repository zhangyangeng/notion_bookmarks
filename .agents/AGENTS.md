# Agent 工作规范

本文件是所有 AI 编码工具（Claude Code / Cursor / Gemini / Codex / WorkBuddy 等）进入本项目的**唯一入口**。
根目录的 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 均为指向本文件的软链接，**只维护这一份**。

> **本文件只写长期成立的内容。** 改造进度、待办清单、当前状态一律不写在这里 ——
> 它们随时间变化，留在规范里会迅速过时，并误导后来接手的人与工具。
> 三类信息的分工见文末「附录」。

## 二、八条铁律

这些是本项目特有的事实，**AI 靠通用经验推不出来**，必须严格遵守。

### 1. 库里的内容大部分不属于项目所有者

线上库中多数条目**继承自上游作者的 Notion 模板**（fork 时整库复制），只有少数为所有者自建。
做功能、做分析、做数据清洗时，**不要把继承内容当作自建数据**来推理用户意图。

归属的判定方法与实测数据见 `docs/references/01-内容溯源审计.md`。

### 2. 已与上游正式分家，不要 merge upstream

本项目的改造方向是**删**（主题、小组件、动画库），而上游的更新方向恰恰是**加**这些东西 ——
`merge upstream` 等于把刚删掉的装回来。只允许 `cherry-pick` 单个 `fix` / `security` 提交。

### 3. Notion 的 `files` URL 一小时过期

Notion 返回的 `iconfile` 是**签名 S3 链接，1 小时后失效**。把它塞进长时间缓存必然 403。
图标走 `iconlink`（外链）或服务端代理，**不要直接缓存 `iconfile`**。

### 4. 不要新增与「收藏网站」无关的功能

时钟 / 天气 / IP 查询 / 热搜 / 自选股这类小组件与项目定位无关，
且每加一个都要在多套主题里各调一遍样式。**这是硬约束，不是建议。**

### 5. 不要每个问题都新建文档

解惑型、澄清型、决策确认型的问题，在对话里答完即可。
只有**有长期价值的定案 / 清单 / 路线图**才写入 `docs/`，且优先**修订已有文档**。

### 6. 包管理统一用 pnpm

保留 `pnpm-lock.yaml`；不要生成或提交 `package-lock.json`。
依赖安全版本锁定在 `package.json` 的 `pnpm.overrides` 中，**改动依赖前先看那里**。

### 7. 下判断前先查 `docs/`

`docs/` 记录了项目所有重大判断，其中一些是**推翻过早期结论**之后才定下的 —— 拿已过时的结论当依据会做错方向。

**修订时直接改原文，不要新起一份文档。** 同一结论只保留一个权威出处。

若文档里找不到答案：**先去实测，再下结论** —— 不要仅凭代码和官方文档推断数据现状。

### 8. 仓库只记录「事实」，不记录「过程」

提交信息、文档、代码注释里写的是**仓库里发生了什么**，不是**这个东西是怎么做出来的**。

| ❌ 过程（不要写）                     | ✅ 事实（该写）                      |
| :------------------------------------ | :----------------------------------- |
| `把 6 份文档收敛为 2 份`              | `新增 A、B 两份文档`                 |
| `经几轮调研后推翻了原判断`            | `明确分类的承载方式改用 relation`    |
| `先试了 A 方案不可行，改为 B`         | `采用 B 方案`                        |

**判据：这句话描述的东西，读者能在本次 diff 或仓库里找到吗？** 找不到，它就是过程。

> **为什么**：过程是 AI 的工作记忆，不是项目资产。写进仓库后，它变成后来者**无法验证、也无法删除**的噪音 ——
> 而读者看到「那 6 份文档」还会真的去找。过程留在 `.workbuddy/memory/`（不进 git），仓库只留结论。

## 四、通用准则

- **语言**：所有回复、代码注释、设计文档使用**简体中文**；代码标识符保持英文。
- **注释**：解释"为什么这样设计"，不解释"是什么"；禁止无意义注释。
  关键位置使用 `NOTE` / `TODO` / `FIXME` 统一标记。
- **分支工作流**：使用功能分支，**避免直接在 `main` 上改动**；分支名需表达意图。
- **推进方式**：分阶段小步走，**一次改动只做一件事**，避免一次性大幅重构。
- **交付标准**：改动完成后至少跑通 `pnpm lint` 与 `pnpm build`。
- **格式**：提交前跑 `pnpm format`（prettier 已配置，2 空格缩进），不要手工调整缩进。

## 附录：三类信息的分工

往这个仓库写东西前，先判断它属于哪一类、该放哪：

| 存放位置 | 放什么 | 寿命 | 是否进 git |
| :--- | :--- | :--- | :--- |
| `.agents/` | 稳定约束：定位、约定、禁止事项、目录规则 | 长期 | 是 |
| `docs/` | 决策记录：定案、清单、方案、路线图 | 中期（会被修订） | 是 |
| `.workbuddy/memory/` | 当前状态：进度、待办、临时结论、踩坑记录 | 短期 | 否 |

**判据：把内容放到 `.agents/` 之前，问一句「半年后还成立吗？」**
不成立 → 放 `docs/`；只是"现在做到哪了" → 放 `.workbuddy/memory/`。
