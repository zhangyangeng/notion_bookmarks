# 项目背景

## 一、这是什么

一个**个人网站收藏站**（导航站），用 **Notion 当内容后台**，Next.js 渲染，部署在 Vercel。
初衷：替代博客里手工维护的收藏帖，同时解决"换设备就要登录 Chrome 账号才能找到书签"的问题。

| 项 | 值 |
| :--- | :--- |
| 线上地址 | https://nav.wrysmile.cn |
| 待迁移的博客旧帖 | https://www.wrysmile.cn/web-nav.html |
| 全量数据接口 | `https://nav.wrysmile.cn/api/links`（公开，可直接取 JSON 做分析） |
| 上游仓库 | `moyuguy/notion_bookmarks` |
| 上游在线 Demo | `portal.ezho.top`（可用于内容比对） |

### 产品定位

**带个人背书、可分享的收藏库。** 不是大而全的门户，也不是纯私人收藏库。

两个使用者，两个面 —— **同一份数据、同一套代码，差一个过滤条件**：

| 面 | 给谁 | 特征 | 内容 |
| :--- | :--- | :--- | :--- |
| 公开面 | 朋友 | 低频、带具体问题、忍耐度为零 | 只展示**已发布**的条目，按推荐度分层 |
| 私人面 | 自己 | 高频、要秒搜到 | 全库控制台 |

**护城河是"点评"，不是"链接"。** 名单网上到处都是，不可复制的是"我试过、我筛过、我有意见"。
分享动作发生在**微信输入框**里，不在网站上 —— 所以设计目标是"这串字符短到愿意记、好到对方一看就懂"。

## 二、技术栈与数据流

### 选型

| 维度 | 选择 | 说明 |
| :--- | :--- | :--- |
| 框架 | **Next.js 15（App Router）** | 单体，前后端同仓 |
| 语言 | TypeScript（`strict: true`） | 另开 `noUnusedLocals` / `noUnusedParameters` / `noImplicitReturns` |
| 样式 | Tailwind CSS 3 + 手写主题 CSS | `tailwind.config.ts` + `src/themes/**/style.css` |
| 内容源 | **Notion API**（`@notionhq/client`） | 充当 CMS，免自建服务器与运维 |
| 状态 | Zustand | 轻量全局状态 |
| 部署 | Vercel | 依赖其 ISR 能力 |
| 包管理 | **pnpm** | 见铁律 6 |

> **选型约束**：不要引入需要自建服务器、自托管数据库或额外运维成本的方案。
> "最小运维"是本项目的硬性前提，不是偏好。

### 数据流

```text
Notion 数据库（链接条目 + 网站配置）
        │
        │  @notionhq/client
        ▼
  src/lib/notion.ts           拉取、字段转换、图标 URL 解析
        │                     （外层用 React cache() 做单请求内去重）
        ▼
  src/app/page.tsx            ISR 缓存层：export const revalidate
        │
        ▼
  src/components/layout/MainContent.tsx    客户端交互容器（分类筛选、滚动联动）
        │
        ├── Navigation.tsx       侧边栏 / 移动端顶栏
        └── LinkContainer.tsx    分类分区
              └── LinkCard.tsx   单张链接卡片
```

**另有一条独立链路**：`src/app/api/links/route.ts` 暴露全量 JSON，供外部读取（分析、迁移脚本都靠它）。
**该接口的响应结构视作对外契约，不要随意改动。**

### 数据访问的关键机制

- **`revalidate` 是唯一有效的缓存开关。** Next 只认路由段的 `export const revalidate`；
  环境变量、模块常量都不会生效（`src/lib/notion.ts` 里曾有过这类死代码）。
- **需要按需刷新时**用 `revalidateTag` / `revalidatePath`，并在 `src/app/api/` 下配独立的触发路由。
- **图标 URL 会过期**：见铁律 3。

## 三、数据模型的设计约定

字段定义**以代码为准**（`src/types/notion/link.ts`）；字段扩展清单与顺序见 `docs/architecture/02-改造路线.md` —— 规范里不重复。

以下是设计层面的长期约定，改动数据模型或条目展示形态时必须遵守。

### 1. `合集` 与 `Tags` 是两个概念，不要合并

| 概念 | 面向 | 用法 |
| :--- | :--- | :--- |
| `合集` | **对外** | 分享单位，名称用**朋友的问法**（如「免费图床」），对方一看就懂 |
| `Tags` | 对内 | 自己的检索维度 |

合并会让两个能力同时失效：既无法"只把这一组分享出去"，也无法"按自己的维度筛选"。

### 2. 可见性是「发布机制」，不是「审查机制」

一条内容的可见性只有三种：**草稿**（还没决定怎么处理，不展示）、**公开**（已发布，进公开面）、**私人**（已决，但只自己看）。

系统要防的是**"未决"**，不是**"敏感"** —— 破解软件、需要特殊网络环境的工具都可以放心存、放心公开，不必因为"内容敏感"而不敢入库。

**写代码时最易踩的两点：**

- `可见性` 的**默认值一律取"不公开"**（`草稿`），永远不要默认公开；
- 外部捕获进来的条目默认落 `草稿`，人工确认后才改 `公开` 或 `私人`。

### 3. `可见性` 与 `推荐` 是两个维度，不要合并

| 字段 | 回答的问题 | 值域 | 默认值 |
| :--- | :--- | :--- | :--- |
| `可见性` | **给不给别人看** | 草稿 / 公开 / 私人 | 草稿 |
| `推荐` | **在库里排多前** | 力荐 / 推荐 / 无 | 无 |

两者正交，因为**同类网站常是互补关系而非替代关系**（A 快但有限额、B 有广告但容量大）——
需要"都公开、但分出主次"。

因此 **「公开但不力荐」是合法且常见的状态**，公开面**不能**只放力荐的条目。

依赖方向：`推荐` 仅在 `可见性 = 公开` 时生效；可见性为草稿或私人时，`推荐` 值被忽略 ——
这样不必额外校验，也不会产生"私人 + 力荐"这类无意义组合的歧义。

### 4. `分类` 与 `合集` 用 Relation，不用 Select

**判据：这个维度需不需要挂东西？** Select 选项只有颜色，装不下 `图标` / `排序` / `开关` / `slug` /
`一句话说明` / `封面` / `可见性`。只要有一项需要，就必须是 Relation 到独立数据库。

更深一层的原因：**Select 的选项表是全表共享且扁平的，无法表达「这个二级分类属于哪个一级分类」。**
所以同一个概念必然会在多个一级分类下被重复登记（实测 `效率工具` 出现在 6 个一级分类下）。

| 维度 | 面向 | 承载 |
| :--- | :--- | :--- |
| `分类` | 对内（结构，用于浏览筛选） | Relation → `分类配置`，层级由其 `上级` 自关联表达 |
| `合集` | 对外（策展，用于分享 `/c/[slug]`） | Relation → 独立「合集」库 |

两者**不是包含关系**：一条链接可以进合集但不适合任何分类，反之亦然。

> ⚠️ **写代码时必须记住的后果**：`src/app/page.tsx` 有一道白名单 ——
> 链接的 `category1` 必须出现在 `getCategories()` 返回的分类名里（该查询带 `Enabled = true` 过滤），
> 否则链接被**静默丢弃**，界面上没有任何提示。凡是"归类缺失"的兜底逻辑，都必须让缺失**可见**，不能丢弃。

## 四、项目决策记录在哪

`docs/` 按性质分目录，**设计与事实分开存放**：

```text
docs/
├── architecture/   # 设计文档：定位、数据模型、双面架构、改造方案
└── references/     # 参考资料：调研数据、审计结果等事实记录
```

现有文档及其主题：

| 文档 | 主题 |
| :--- | :--- |
| `architecture/01-产品定位与架构设计.md` | 站点定位、数据模型约定、双面架构、分享层设计 |
| `architecture/02-改造路线.md` | 基底取舍、减法/加法清单、既有缺陷修复、改造顺序 |
| `references/01-内容溯源审计.md` | 库内内容的来源审计方法与结论（可复现） |

**引用规则：** 同一结论只保留**一个权威出处**，不在多处重复。
判定与设计以 `architecture/` 为准，事实数据以 `references/` 为准。
