# 代码提交

## 前置约定

- 遵循 **Angular Commit** 规范，**提交信息使用中文**。
- **绝不擅自提交**：不要自动执行 `git add`，更不要自动执行 `git commit`。
  改动完成后，把「涉及的文件、各改了什么、提交信息草案」呈现给所有者，**等他确认再提交**，
  且只提交他确认的范围。具体流程见 1.1 与 1.7 —— **这两节是硬约束，不得跳过**。
- **使用功能分支**，避免直接在 `main` 上改动。若当前在 `main` 上，先根据需求描述切出新分支，分支名需表达意图。
- 包管理用 **pnpm**，保留 `pnpm-lock.yaml`；**不要提交 `package-lock.json`**。
- 提交前确保 `pnpm format` 已执行（见 [02-编码规范](./02-编码规范.md)）。

## 一、工作流程

### 1.1 读取暂存区

1. 执行 `git diff --cached --name-status` 获取已暂存文件列表。
2. **若没有任何已暂存修改**（命令无输出），停止执行并提示用户：
   > `未检测到已暂存的修改。请先使用 git add 暂存您想要提交的代码。`
3. 执行 `git diff --cached` 获取详细变动内容。

> **不要自动 `git add`。** 用户未明确说明时，只提交已暂存的内容，不要替他决定暂存范围。

### 1.2 判断提交类型（type）

对暂存内容做语义分析，确定类型。**优先级：`feat` > `refactor`/`perf` > `docs`**。

| type | 适用场景 |
| :--- | :--- |
| `feat` | 新增功能，或在已有功能上添加新业务逻辑 |
| `fix` | 修复缺陷 |
| `refactor` | 代码重构，不改变外部行为 |
| `perf` | 性能优化（加载速度、渲染开销、包体积） |
| `style` | 仅格式调整（缩进、空格、分号），不改逻辑 |
| `docs` | 文档、README、说明文件，或仅改代码注释 |
| `chore` | 构建流程、依赖升级、配置调整 |
| `test` | 测试用例的增删改 |

### 1.3 分析 scope（影响范围）

1. 从 `--name-status` 输出中过滤出源码与配置文件（`.ts` `.tsx` `.js` `.mjs` `.css` `.json` `.yaml` 等）。
2. **恰好 1 个** → 取文件名（去后缀）。例：`src/components/ui/LinkCard.tsx` → `LinkCard`
3. **2 个以内** → 文件名用 `, ` 拼接。例：`LinkCard, CategoryIcon`
4. **0 个或超过 2 个** → scope 留空

### 1.4 生成标题

```text
有 scope：<type>(<scope>): <不超过 20 字的中文摘要>
无 scope：<type>: <不超过 20 字的中文摘要>
```

### 1.5 生成正文

- 用无序列表列出具体改动点，每项**一句话讲清"改了什么、为了什么"**。
- **绝对不要描述代码实现细节**（不要写"把 useState 换成 useRef"这类），只说行为与目的。
- **绝对不要描述改动过程**：中间稿、试错的方案、第几轮修订都属于过程，读者在 diff 里看不到它们。

  | ❌ 过程（不要写）              | ✅ 事实（该写）                |
  | :----------------------------- | :----------------------------- |
  | `把 6 份文档收敛为 2 份`       | `新增 A、B 两份文档`           |
  | `修正上一版关于 X 的误判`      | `明确 X 的承载方式为 relation` |

  判据：**这句话描述的东西，读者能在本次 diff 里找到吗？** 找不到就不要写（详见 `AGENTS.md` 铁律 8）。

```text
feat(LinkCard): 增加点评字段展示

- 卡片底部增加点评行，最多显示两行并支持悬停查看全文
- 长标题自动截断，避免撑破卡片布局
```

### 1.6 标注编码工具

在正文末尾**固定加一行**，标明本次改动由哪个工具完成，便于后续追溯：

```text
编码工具：Claude Code
```

常用值：`Claude Code` / `Cursor` / `Gemini` / `Codex` / `WorkBuddy` / `DeepSeek Harness`。
（若需要被 GitHub 统计为贡献者，可改用标准格式 `Co-authored-by: <名称> <邮箱>`。）

### 1.7 预览并等待确认

在对话中以代码块展示生成的提交信息，**等待用户确认后再执行**：

```text
===== 生成的 COMMIT（预览，尚未提交）=====
<完整提交信息>
=========================================
确认无误请回复「确认」或「提交」，我将执行 git commit。
```

用户确认后执行：

```bash
git commit -m "<标题>" -m "<正文>"
```

## 二、拆分原则

- **一次提交只做一件事。** 大规模格式调整（如统一缩进）必须**单独成一个 `style` 提交**，不要和功能改动混在一起 —— 否则 diff 全是噪音，无法 review。
- 功能改动与依赖升级分开提交。
- 重构与行为变更分开提交。
