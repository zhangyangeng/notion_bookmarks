# 工作环境

本项目在 **WorkBuddy 的 worktree 布局**下开发，本文内容以此为前提。
如果换到常规克隆（`git clone` 后直接在仓库目录内工作），第一、二节需要重新验证。

---

## 一、git 目录不在工作区内

worktree 的 git 目录挂在主仓库下，而不是工作区里：

```text
工作区     /Users/wrysmile/WorkBuddy/Worktrees/notion_bookmarks/<worktree>/
git 目录   ~/WorkSpace/notion_bookmarks/.git/worktrees/<worktree>/
```

**后果**：git 的**写操作**（`add` / `commit` / `branch` / `merge` / `cherry-pick`）需要对本工作区**之外**的
那个目录取得写入授权；只读操作（`status` / `log` / `diff` / `show`）不受影响。

**约定**：git 写操作**串行执行**，不要与只读命令混在同一条命令里。
一次授权覆盖多个动作时，失败后难以定位是哪一步出的问题。

> 如需减少授权次数，可在沙箱配置的 `sandbox.extraAllowWrite` 中加入该 git 目录。
> 修改后需重启会话才生效。

---

## 二、`index.lock` 残留会阻塞全部写操作

**机制**：git 在写入索引前先创建 `index.lock`。本项目的 git 目录在工作区之外（见第一节），
沙箱对该路径的写入需要授权；授权未及时给出或被拒绝时，git 进程中断，
**留下一个 0 字节的锁文件**。而 git 只清理自己正常结束时创建的锁 —— **残留的锁不会自愈**。

**表现**：

| 操作 | 结果 |
| :--- | :--- |
| 读操作 `status` / `log` / `diff` / `show` | 正常（大多不加锁） |
| 写操作 `add` / `commit` / `checkout` / `merge` | 全部失败 |

**典型报错**：

```text
fatal: Unable to create '.../index.lock': File exists.
fatal: unable to write new index file
```

> **一次中断 = 之后每次写操作都撞墙**，表现为"时好时坏"。
> 不要把这种时好时坏当随机故障 —— **读正常而写失败，几乎总是锁或权限问题，不是内容问题。**

**另一个并发来源**：编辑器（VSCode + GitLens，`git.autofetch: true`）也会在后台执行 git 操作，
可能持握同一个锁，加剧争抢。它使问题更容易复发，但不是首次产生残留锁的原因。

**处理四步，缺一不可：**

1. **确认无活跃 git 进程**：`pgrep -fl git`。
   注意 `@github/copilot` 这类编辑器扩展不是 git 进程，不要被它的名字误导。
2. **确认锁文件为 0 字节**。
3. **删除锁文件**。
4. **重新执行原命令并验证结果**（不要假定它成功了）。

> ⚠️ 锁文件存在**不代表**可以删。有 git 进程正在运行时删锁，会破坏它正在写入的索引。
> 第 1、2 步是安全前提，不能跳过。

## 三、评估分支价值用 `git show --stat`，不用对比 diff

判断一条长期分支还值不值得合并时，看**它这一支自己提交了什么**：

```bash
git show <branch> --stat
```

**不要**用 `git diff <当前分支> <branch>`：当分支的基线明显落后于当前分支时，
这个 diff 会把当前分支后来新增的内容显示成「分支要删掉的东西」，
结论与事实相反（**基线越老，假象越大**）。
