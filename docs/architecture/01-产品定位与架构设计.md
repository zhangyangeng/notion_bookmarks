# 产品定位与架构设计

> 本文档回答：这个站点**是什么**、**为什么这么设计**。
> 数据模型与双面架构的长期约定都在这里；具体改什么、按什么顺序改，见 [`02-改造路线.md`](./02-改造路线.md)。

---

## 一、定位：一个库，两个面孔

### 1.1 两个用户，两种需求

站点要同时服务两类人，而他们的需求几乎相反：

| 维度 | 🧑‍🤝‍🧑 朋友（访客） | 🐱 自己（主人） |
| :--- | :--- | :--- |
| 触发 | 一个**具体问题**（「有没有免费图床」） | 刷到一个好站 / 想找旧收藏 |
| 频率 | 极低，一年几次 | 高，几乎每天 |
| 入口 | **你主动发给他的链接** | 站点首页 / 搜索 |
| 想要 | **3–5 个，带你的点评，能立刻用** | 全部，能秒搜到 |
| 停留 | 30 秒 | 随缘 |
| 失败模式 | **链接挂了 / 找不到想要的 → 他不会问你第二次** | 存了找不到 / 忘了存过 |
| 忍耐度 | **零** | 很高 |

### 1.2 不是二选一，是同一份数据的两种投影

定位问题曾经被当成「做门户还是做收藏库」的二选一。**这是伪命题。**

```
              一个数据源（Notion 录入 → 快照层）
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
   ┌────────────────────┐          ┌────────────────────┐
   │  公开面 · 精选橱窗   │          │  私人面 · 全库控制台 │
   │  ────────────────  │          │  ────────────────  │
   │  · 可见性 = 公开    │          │  · 全部条目         │
   │  · 按合集组织        │          │  · 搜索 / 待整理     │
   │  · 朋友打开即可用    │          │  · 私人备注          │
   └────────────────────┘          └────────────────────┘
        nav.wrysmile.cn               同域名 + 轻口令
```

**同一份数据、同一个代码库，差一个 `filter`。不是两个站点，是两次渲染。**

**核心收益：公开面的维护量与收藏总量解耦。** 你收藏 500 条、只公开 30 条，公开面就只有 30 条需要你操心 —— 而不是每存一条就给自己加一份债。

### 1.3 护城河是「点评」，不是「链接」

朋友为什么不直接 Google？Google 给他 50 个，**你给他 5 个，并且告诉他为什么**。

> 「我收藏了几个我**体验比较好的**，你自己瞅瞅。」

**这句话就是全部的产品价值。** 名单网上到处都是，不可复制的是「**你试过、你筛过、你有意见**」。

推论：上游那套字段里**没有一个能装下「你的意见」** —— `desc` 是站点自述，不是你的评价。所以 `点评` 不是锦上添花，**它是产品的核心资产**，而且必须是短句（朋友在微信里 3 秒要能看懂「A 最好用，B 有广告，C 快但有限额」）。

## 二、数据模型的设计约定

字段的**类型定义以代码为准**（`src/types/notion/link.ts`）；新增字段的完整清单与添加时机见 [`02-改造路线.md`](./02-改造路线.md) 第三节。本节只固定那些**长期成立的设计原则**。

### 2.1 `合集` 对外，`Tags` 对内

| 字段 | 面向 | 性质 |
| :--- | :--- | :--- |
| `合集` | **对外** | 朋友看得懂的自然语言（「免费图床」「Win 必装」） |
| `Tags` | **对内** | 你自己筛选用的机器维度（开源 / 免费 / 需要🪜） |

**两者不要混用。** 一个混用，两个能力同时失效。

### 2.2 `可见性` 与 `推荐` 正交，不可合并

| 字段 | 回答的问题 | 值域 | 默认值 |
| :--- | :--- | :--- | :--- |
| `可见性` | **给不给别人看** | 草稿 / 公开 / 私人 | `草稿` |
| `推荐` | **在库里排多前** | 力荐 / 推荐 / 无 | `无` |

这两件事必须分开，因为**同类网站常常是互补关系，不是替代关系** ——
免费图床里 A 快但有限额、B 有广告但容量大，**两个都值得给朋友看，但首推只有一个**。

由此得出一条容易写错的规则：

> **公开面的取数是 `可见性 = 公开`，不是 `推荐 = 力荐`。**
> `推荐` 只影响公开面内部的**排序与标注**。
> 因此「**公开但不力荐**」是合法且常见状态。

依赖方向：`推荐` 仅在 `可见性 = 公开` 时生效；可见性为草稿或私人时 `推荐` 值被忽略。这样不必额外校验，也不会产生「私人 + 力荐」这类无意义组合的歧义。

### 2.3 可见性是「发布机制」，不是「审查机制」

```
❌ 审查视角：敏感 / 非敏感  →  藏 / 露      ← 让人不敢存东西
✅ 发布视角：未决 / 已决    →  草稿 / 发布   ← 鼓励存东西
```

**系统要防的不是「敏感内容」，是「你还没决定的内容」。**

这条修正了一个容易犯的直觉错误：「破解软件 + 解压密码」这类条目，第一反应是"必须藏起来"。**恰恰相反** —— 它是你主动点头要分享的东西，本来就该公开。真正的风险是**未经你确认的内容自动泄露**，而那个问题由 `可见性` 默认值解决：

- 外部捕获进来的条目**一律落 `草稿`**（默认不公开），人工确认后才进 `公开`；
- 因此**程序完全不需要判断内容敏不敏感** —— 那个判断本来就不该交给程序。

三条收益同时成立：① 存东西零心理负担；② 升级、破解类内容可以放心公开；③ 不存在手滑泄露。

> 由此得出一条硬约束：**可见性必须在数据层控制（Notion 字段），不能靠前端过滤。**
> 前端隐藏等于没隐藏 —— URL 一猜就出来了。

### 2.4 `分类` 与 `合集` 是「实体」，不是「标签值」

Notion 里表达归类有两条路，本项目的选择是明确的：

| | 载体 | 适用 |
| :--- | :--- | :--- |
| ❌ | `Select` / `Multi-select` —— 值只是一个**属性下拉框里的字符串** | 仅适合「用完即弃、无需管理」的临时维度 |
| ✅ | `Relation` → 独立数据库 —— 值是一条**记录** | `分类`、`合集` 这类需要被管理、需要挂元数据的维度 |

**判据只有一条：这个维度需不需要挂东西？**
Select 选项**只有颜色**，装不下 `图标` / `排序` / `开关` / `slug` / `一句话说明` / `封面` / `可见性`。只要其中有一项需要，就必须是 Relation。

更关键的是**约束能力**：Select 的选项表是**全表共享且扁平**的，无法表达「这个二级分类属于哪个一级分类」。于是在多个一级分类下重复登记同一个概念，成了必然会发生的熵增（实测：`效率工具` 出现在 6 个一级分类下）。

两条长期约定：

1. **`分类` 用 Relation → `分类配置`**，层级由该库的 `上级` 自关联表达。
   二级分类因此成为**可管理、可排序、可关停、可挂图标**的记录，而不是下拉框里的一个字符串。
2. **`合集` 用 Relation → 独立数据库**，且**不与 `分类` 混用**：
   - `分类` 回答「它属于哪」—— **对内**，结构维度，用于浏览与筛选；
   - `合集` 回答「我发给朋友看什么」—— **对外**，策展单位，用于分享（`/c/[slug]`）。

   两者**不是包含关系**：一条链接可以进合集但不适合任何分类，反之亦然。
   而且 `合集` 需要 `slug` / 一句话说明 / 封面 / 排序 —— 这些只有记录装得下，**Select 装不下**
   （完整字段清单见 [`02-改造路线.md`](./02-改造路线.md) 3.7）。

> ⚠️ 这条约定的反面代价是实测出来的：用 Select 承载分类，会出现「链接上写着分类名、`分类配置` 库里另有记录」两个互不相认的事实源。
> 两者不一致时**链接会被静默丢弃**（线上 28 条 / 12.7% 在首页不存在且无任何提示），详见 [`02-改造路线.md`](./02-改造路线.md) 的 3.6 与 4.1。

> 📌 **这不是「提前重排信息架构」。** 哪些概念该归到哪一类（分类的**内容**）仍然等搜索上线后再修（见第六节）；
> 这里确定的只是分类的**承载方式**（分类的**载体**）。

### 2.5 `补充内容` 放页面正文

每条链接除了属性栏，还有一块**页面正文** —— 在 Notion 里点开该条记录、属性栏下方那块。
解压密码、安装说明、同类替代品、源码仓库地址这类「点开之后才需要」的信息放这里。

**三条由承载方式直接决定的约束：**

1. **正文不参与检索。** Notion 的列表接口只返回属性，正文属于另一份资源，要逐条另发请求才能拿到 ——
   所以补充内容不在前端搜索的索引里。
2. **只能经服务端拉取。** `NOTION_TOKEN` 没有 `NEXT_PUBLIC_` 前缀，只存在于服务端；浏览器手里没有钥匙。
3. **拉取发生在点开时。** 不在构建期全量拉 —— 那会让构建时间随条目数线性增长。

> ⚠️ **`NOTION_TOKEN` 永远不得加 `NEXT_PUBLIC_` 前缀。** 加了前缀，它的值会在构建时被内联进浏览器可下载的 JS，
> 等于把**整个授权库（含未公开条目）**的读写权公开挂在网上，且改环境变量也挽不回来 —— 止损只能去 Notion 撤销集成。

取数链路与实现清单见 [`02-改造路线.md`](./02-改造路线.md) 3.8，界面形态见 [`03-界面设计.md`](./03-界面设计.md) 4.8。

## 三、分享层：短链是入口，不是站内栏目

### 3.1 分享动作发生在微信输入框里，不在网站上

朋友问「有没有免费图床」，真实动作是**直接在微信输入框里打一串字符** —— 不是「打开网站 → 找到合集 → 复制链接 → 切回粘贴」。

所以设计目标不是「网站上有个好找的按钮」，而是：

> **那串字符要短到你愿意记，好到对方一看就懂。**

### 3.2 两条路径，都不需要先进站找合集

| 路径 | 你打什么 | 朋友看到什么 | 适用 |
| :--- | :--- | :--- | :--- |
| **万能路径** | `nav.wrysmile.cn` | 首屏是「**你常被问到的事**」入口 → 一眼看到自己在问的那件 | 99%，零思考，永远能用 |
| **精确路径** | `nav.wrysmile.cn/c/tuchuang` | 直接落到那 5 条 + 你的点评 | 想直接甩答案 |

### 3.3 短链命名

**用英文短词，不用拼音** —— 因为你要**手打**，英文在键盘上成本更低。
另一个好处：**短链本身就是合集的 id**，不用再维护一套映射。

**字符集只允许小写英文和数字** —— `^[a-z0-9]{2,24}$`，不用连字符、下划线或中文。
完整的字段定义与唯一性校验规则见 [`02-改造路线.md`](./02-改造路线.md) 3.7。

```
/c/tuchuang    免费图床
/c/windows     纯净系统 / 系统镜像
/c/win         桌面效率工具（Everything / Pixpin / Quicker…）
/c/tools       在线小工具
/c/resume      简历模板
/c/books       电子书
```

需要记住的**不超过 10 个**，因为朋友会问的事就那么几类。

### 3.4 首屏要改的是「语义」，不是「布局」

现在首屏是分类目录（`AI工具(66)` / `开发资源(50)`），要改成「**朋友会问的问题**」：

| 现在 | 改成 |
| :--- | :--- |
| AI工具 (66) | 找 AI 工具 |
| 开发资源 (50) | 找前端 / 后端资源 |
| 设计资源 (39) | 找图标 / 配色 / 图片 |
| ——（不存在） | 找免费图床 |
| ——（不存在） | 装纯净 Windows |

**改的是标题，不是结构。** 成本极低，但它决定朋友打开链接后 3 秒内是「找到了」还是「这是什么鬼」。

## 四、捕获与整理

### 4.1 捕获能力一直存在：Save to Notion

上游明确推荐 **Save to Notion** 浏览器扩展，它自动抓取标题 / URL / 描述 / favicon，且支持：

- **Form 模板** —— 可为不同用途建多个表单
- **锁定字段默认值**（"Lock properties to the form as defaults"）
- 强制预设标签

> ⚠️ 已知缺口：**Save to Notion 没有移动端**（浏览器插件，手机用不了）。移动端走 iOS 快捷指令 / PWA `share_target`。

### 4.2 真正的堵点在「整理」，不在「捕获」

插件的产物是**「生的」**。一条链接抓进 Notion 之后，还得改名字、选分类、补标签 —— **每存一条 = 3 个决策**，一次存 15 条就是 45 个决策。

于是真实工作流变成：**兴致来了猛存一批 → 整理到一半累了 → 停 → 下次想不起当时为什么存 → 干脆不存。**

> **捕获是零成本的，整理是昂贵的。而原设计假设了「捕获完就完事」。**

**解法不是再造一个捕获通道，是让捕获物默认不需要立刻整理** —— 见 [`02-改造路线.md`](./02-改造路线.md) 的「最小第一步」。

### 4.3 「多端同步」这件事已经解决了

「任意设备、任意浏览器都能访问」—— **有域名有网站，网站本身就是最干净的同步层**，这是它相对浏览器书签唯一不可替代的优势。

真正缺的不是「同步」，是**「存」的入口跨端**。浏览器书签的病根是：**「存」被锁死在 Chrome 里，而「读」你想在任何地方**。

| 设备 | 现在怎么存 | 应该怎么存 |
| :--- | :--- | :--- |
| 桌面（任意浏览器） | Chrome 书签 → 换设备就没了 | 书签小工具 / Save to Notion |
| iPhone / iPad | Safari 书签 → 找不到 | 快捷指令 → POST 到自己的站 |
| Android | 同上 | PWA + `share_target` |
| 任何设备兜底 | Notion App（要翻进表格） | 打同一个「收件箱」 |

统一设计：**所有入口都打到同一个收件箱**，存进来的先落 `草稿`，心情好了再归类。好处是以后换后端只改这一处。

## 五、分享场景的非功能约束

朋友是「顺一眼」，这几条不满足，前面所有设计都白搭：

1. **快。** 转 3 秒朋友就退了。→ 公开面**必须纯静态 / 边缘缓存**，绝不能在请求里实打实打 Notion API（国内访问慢 + 3 req/s 限流）。
2. **可达。** 人在北京、朋友大概率也在国内。托管位置的国内可达性必须成立 —— 这是「给朋友看」的硬约束。
3. **不发死链。** 博客原文里那句「（目前网站已失效）」就是手工版死链巡检。进入分享语境后，死链从「自己的小麻烦」升级为「**丢面子**」。
4. **OG 卡片。** 微信 / 飞书里分享出去长什么样，直接决定朋友点不点。不做就像小广告。
   机制、微信侧的硬边界与实现约定见第六节。

> ⚠️ 朋友大概率在**微信内置浏览器**里打开 —— 微信对域名可达性、`target=_blank`、长按复制都有脾气，必须实测。

## 六、分享卡片：机制、微信限制与实现约定

### 6.1 卡片来自页面元信息，不来自站内按钮

微信 / QQ / 飞书 / 钉钉 / 微博读的是页面的 **Open Graph**（`og:title` / `og:description` / `og:image`）。
站内既不需要分享按钮，也不需要 JS-SDK，**卡片内容就等于页面 `<head>` 里的元信息**。

> X（推特）读的是 `twitter:*`。源码中未声明这组标签，但 **Next.js 的元数据 API 在缺省时会自动从 `openGraph` 派生**，
> 页面输出里仍有完整的 `twitter:card` / `twitter:title` / `twitter:description` / `twitter:image`，内容与 OG 一致。
> 即：无需为 X 单独维护，也不要因为「源码里没有」就以为输出里也没有。

### 6.2 微信的外链限制（硬边界，改代码解决不了）

同一个链接，**从哪个入口进去，决定分享出来是卡片还是纯文本**：

| 动作 | 分享出去的样子 |
| :--- | :--- |
| 聊天输入框里直接粘贴链接 | **纯文本 URL** |
| 扫码、或从已有卡片点开 → 页面内「转发给朋友」 | 卡片 |
| 收藏后从收藏打开 → 再转发 | 卡片 |
| 从公众号文章进入 → 再转发 | 卡片 |

成因：微信无法判断第三方外链的安全性，对外链平台**设信用分级** —— 大站 / 老域名待遇更好，规则不公开。

线上实测排除了三种常见猜测：**与 OG 配置无关**（从卡片点开时标题、描述、图全对）、**与微信版本无关**、
**与抓取缓存无关**（缓存只影响改完多久能看到新结果，不影响形态）。

于是本站可控的杠杆只有一条：**把 OG 做对，让「能出卡片」的那条路径里卡片是好看的**。
至于让聊天框里直接粘贴的第三方外链变成卡片 —— 做不到：JS-SDK 管的是「页面已打开、点分享」时的自定义，
页面没打开就无从生效；第三方卡片服务同样依赖「从卡片进入」这条路。

### 6.3 两级结构 + 一张兜底图

| 层级 | 声明位置 | 覆盖范围 |
| :--- | :--- | :--- |
| 站点级（兜底） | `src/app/layout.tsx` 的 `generateMetadata` | 全站：首页、分享页，以及此后新增的任何页面 |
| 合集级（覆盖） | `src/app/c/[slug]/page.tsx` 的 `generateMetadata` | 该合集页；`og:url` 指向本页自身 |

- **配图**：合集填了封面就用封面，未填退回站点兜底图 `public/og.png`（1200×630，浅色主题）。
  因此补封面不需要改代码。
- **微信只取中心正方形**：1200×630 的图在聊天列表里被裁成中心 `630×630`，再压到约 **96px** 显示
  （实测：截图里两张卡片的缩略图均为 96×96，与原图中心裁切结果逐像素对应）。
  由此得到**字号下限**：96px 显示尺寸下，原图里低于 90px 高的元素必然糊掉。
  **图里只放单个大字或字母标，不放说明书式的副文案与域名** —— 那些字在那个尺寸下等于噪点。
- **画幅取 1200×630**（1.91:1 的通用比例）：微信消费其中的中心正方形，两侧留给按宽幅展示的平台。
  **缩放比只由被裁正方形的边长（即图高）决定 —— 图越高，字缩得越小。**
  因此不把画幅做成大正方形：同样的字号放进去，微信里的显示尺寸反而更小。
- **站点地址兜底**：`NEXT_PUBLIC_SITE_URL` 未配置时退回 Vercel 部署域名，避免把 `localhost` 写进 `og:url`。

### 6.4 图和描述各说一件事

卡片上图与描述同时出现，分工要分明：**图说「这里有什么」，描述说「为什么会有这个站」**。
让描述复述图上的字，等于白白浪费一个位置。

## 七、明确不做的事

- **❌ 不加与「收藏网站」无关的功能。** 时钟 / 天气 / IP / 热搜 / 自选股这类小组件与项目定位无关，且每加一个都要在多套主题里各调一遍样式。
- **❌ 不自托管 Karakeep / Linkwarden。** 那是「加运维」不是「最小运维」（Postgres + Meilisearch + Chrome + 应用四件套）。**抄思路，别抄部署。**
- **❌ 不上重型向量数据库。** 2000 条数据的向量检索用「预计算 + 内存内余弦相似度」就够了，几百 KB 的事。别引入需要常驻服务的家伙。
- **❌ 不加用户系统 / 协作 / 多租户。** 单用户场景，朋友看完就走，不需要登录。私人面用轻口令即可。
- **❌ 不为「功能丰富」牺牲捕获速度。** 收藏库的第一性能指标是**存一条要几秒**。
- **❌ 不提前改信息架构。** 分类体系的腐烂是**人脑维护分类的必然熵增**，不是错误。等搜索跑起来、真用起来，自然会知道该怎么合 —— 现在改等于闭着眼睛重排书架。
  （例外：分类的**承载方式**要从 Select 换成 Relation —— 那不是重排内容，是换掉漏水的容器，见 2.4。）
