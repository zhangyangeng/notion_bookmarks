## 一、基底取舍：留，但要做一次「砍到骨架」的大减法

| 问题 | 答案 |
| :--- | :--- |
| 还要不要这个基底？ | **留。** |
| 为什么 | 问题不是**技术选型错**，是**功能堆多了 + 定位继承错了**。前者可以删，后者可以改 |
| 什么时候才该重写 | 做减法时发现要改的代码 > 60%，或新能力必须重构核心数据流 |

### 留下它的理由

1. **约束条件没变。** 头号理由是「不想有服务器开销和运维」→ **Notion 当 CMS 仍是这个需求的最优解**，换任何方案都要重新解决「免运维」。
2. **架构选型是对的。** `Next.js App Router + Notion API + Vercel` 是「个人收藏站」的标准答案，没有「换掉它就能解决问题」的替代品。
3. **它有一份容易被忽略的真资产。** Save to Notion 捕获链路 + 一份完整的中文官方文档站。换基底等于全丢。
4. **重写成本被高估 —— 要删的和要留在代码上是分离的。**

   | 要留的（标准件） | 要删的（继承的负债） |
   | :--- | :--- |
   | Notion API 读取层 | 多套主题（≈1679 行 CSS） |
   | 分类 → 卡片网格渲染 | 小组件（时钟/天气/IP/热搜/自选股） |
   | 部署配置、环境变量 | framer-motion 动画 |
   | 图标处理（骨架） | lucide 全量导入 |
   | 组合成页面的结构 | 轮询定时器图标加载 |

   **删比写便宜十倍。** 砍完右边这列，代码量可能少 40%，而左边一行都不用重写。

5. **站点已在线可用。** 重写意味着 `nav.wrysmile.cn` 要下线一段时间，而「站点不可用」是现在最不需要的风险。

### 什么时候才真的重写

> **做减法时，如果发现「要改的代码 > 60%」，或者新能力（搜索 / 分享页 / 收件箱）全都必须重构核心数据流才能支持 —— 那就重写。**

从当前代码结构看不会触及这条线，但留着这条判据，做减法做到一半时可以回头验证。

## 二、减法清单（先砍，后加）

**原则：先做减法。** 每加一个功能都要在多套主题里各调一次样式 —— **不先砍主题，加法全是白干**。

| # | 负债 | 证据 | 处理 |
| :--- | :--- | :--- | :--- |
| 1 | **多套主题** | ≈1679 行手写 CSS（`bauhaus` 439 / `macintosh-1984` 384 / `cyberpunk` 231 / `simple` 162 / `theme.css` 463），且 `theme === 'bauhaus-primary' ? ...` 这类分支已渗进组件逻辑 | **砍到 1 套：保留 `simple`**，删 `bauhaus` / `macintosh-1984` / `cyberpunk`。明暗切换保留，并改为「**默认跟随系统 + 可手动指定**」——见下方说明 |
| 2 | **小组件** | 时钟 / 天气 / IP / 热搜 / 自选股 —— 与「收藏网站」零关系，却占了可观的维护面 | **全删** |
| 3 | **framer-motion** | 每张卡片都挂 `<motion.a whileHover>` + `<motion.div>`，200 张卡 = 200 个 motion 实例 | 删，改 CSS `transition` |
| 4 | **lucide 全量导入** | `import * as Icons from 'lucide-react'`（`Navigation.tsx:6`、`LinkContainer.tsx:6`）→ 打包器无法 tree-shake，1000+ 图标进产物 | 按需导入。**`feature/perf-stage-1-optimization` 分支已在做（`CategoryIcon.tsx`），直接合** |
| 5 | **图标轮询定时器** | `OptimisedLinkIcon` 与 `LinkCard` 各挂一个 `setInterval(…, 1000)` 轮询 `image.complete`，外加 4 秒超时定时器与 3 个 `useEffect`。200 张卡 = **峰值数百个定时器每秒在执行**（长列表卡顿主因） | 删，只依赖 `onLoad` / `onError` |
| 6 | **假「最近更新」** | `LinkContainer.tsx:108` 显示的是 `new Date()`，**永远是访问者当前时间** | 删，或改真实数据时间 |
| 7 | **冗余 Navigation** | `MainContent` 渲染两份 `<Navigation>`，而组件内部本来就同时渲染移动端 + 桌面端 → DOM 里四套导航；且 `fixed w-[300px]` 与 `sticky w-[280px]` 定位策略打架 | 删冗余，统一为一种定位策略 |
| 8 | **滚动监听** | `MainContent.tsx:73` 每个 `scroll` 事件都 `querySelectorAll` + 读 `offsetTop`，无节流 → 强制同步布局 | 改 `IntersectionObserver`，或至少 rAF 节流 |

### 主题收敛的完整要求（定案）

**保留什么**：`simple` 一套设计语言（明暗两版样式一起留）。

**删什么**：`bauhaus` / `macintosh-1984` / `cyberpunk` 三套设计语言。

**明暗行为**：默认**跟随系统**（`prefers-color-scheme`），同时允许用户**手动指定**浅色 / 深色。

> **这两件事其实是同一件事。** 现状不支持跟随系统 —— `ThemeProvider.tsx` 写死 `enableSystem={false}` + `defaultTheme="bauhaus-primary"`。
> 之所以用不上 `next-themes` 的系统跟随，正是因为**主题 id 把「设计语言」和「明暗」编码在了一起**（`simple-light` / `simple-dark` / `bauhaus-primary` / `cyberpunk-dark`…），
> 而 `enableSystem` 要求主题值只有 `light` / `dark` 两态。
> 收敛到一套设计语言后，主题值自然退化为 `light` / `dark` / `system` 三态 —— **跟随系统从「实现不了」变成「一个配置项」**。

**不砍的**：分类体系的腐烂（`效率工具` 跨 6 个一级分类）—— **先别重排**，理由见设计文档第六节。但分类的**承载方式**要换，见 3.6。

**砍完的预期收益**：首屏体感明显变快（滚动卡顿主因是定时器 + 全量渲染）、维护成本大幅下降、后面加功能不用改 5 遍。

## 三、加法清单

### 3.1 字段扩展

现有字段：名称 / 链接 / 图标 / 描述 / `category1` / `category2` / `Tags`。改动如下：

| 字段 | 面向 | 值域 / 承载 | 默认 | 何时做 |
| :--- | :--- | :--- | :--- | :--- |
| `可见性` | 对内 | select：草稿 / 公开 / 私人 | `草稿` | **第 3 步** |
| `推荐` | 对外 | select：力荐 / 推荐 / 无 | `无` | 第 4 步 |
| `分类` | 对内 | **relation → `分类配置`**（取代 `category1` + `category2`） | 空 | 第 5 步 |
| `合集` | 对外 | **relation → 新建「合集」库**（库的字段设计见 3.7） | 空 | 第 6 步 |
| `点评` | 对外 | rich_text（短句） | —— | 第 6 步 |

> 设计与职责边界（`可见性` 与 `推荐` 正交、`合集` 与 `Tags` 分工、为什么必须是 relation 而不是 select）见设计文档第二节，此处不重复。

**第二批（按需再加，不要一次上）**：

- `属性`（客观事实：需要🪜 / 开源 / 免费 / 自托管）
- 保鲜状态（在用 / 待验证 / 已失效）—— 死链巡检的落点

一次加太多字段会让分诊决策重新变贵，那就白改了。

> **迁移提示**：现有 `tags` 里的 `力荐👍` 18 条可直接迁移成 `推荐 = 力荐`，零浪费。

### 3.2 最小第一步：让「整理」变成可延迟的动作

**这是全项目性价比最高的一步** —— 改动极小，直接命中「整理堵点」。

```text
动作 1 · Notion 加 `可见性` 字段
         类型 Select：草稿 / 公开 / 私人，默认 草稿

动作 2 · Save to Notion 新建一个 Form
         `可见性` 锁定为 `草稿`（利用插件的"锁属性为默认值"）
         其余字段（名称 / URL / 描述 / 图标）保持自动抓取
         ⚠️ 分类不要在这里填 —— 见 3.6 的说明

动作 3 · 公开面只展示 `可见性 = 公开` 的条目
         一个 filter 的事（私人面照旧显示全部）
```

效果：

```text
改造前：看到好站 → 保存 → 立刻要决定分类/改名/打标 → 累 → 不存了
改造后：看到好站 → 保存 → 完事（零决策） → 攒一批再批量分诊
```

**从「每存一条做 3 个决策」变成「想存就存，整理可以拖到周末」。** 而且批量处理的单价远低于逐条 —— 一次性面对 30 条，注意力是连贯的。

> 可选进阶：新建独立的「收件箱」数据库（只有 URL / 标题 / 抓取时间），Save to Notion 直接存那里。**先做上面的三步版就够了**，别一次上两个机制。

### 3.3 搜索（Cmd+K）

> **状态：已上线。** 界面形态（唤起方式、快捷键符号、面板配方）见 [`03-界面设计.md`](./03-界面设计.md) 4.5，此处只记选型取舍与重新评估的条件。

到 500 条时，**搜索框才是主界面**，卡片网格退为次要。当前远未到这个量级 —— 搜索是**备用入口**，不是主界面。

200–2000 条纯前端检索即可，**零后端成本**。

#### 选型：手写实现，不引 `cmdk` / `fuse.js`

| 采用 | 否决 | 理由 |
| :--- | :--- | :--- |
| 手写面板 `SearchPalette.tsx` | `cmdk` | 需要的只是「输入框 + 结果列表 + ↑↓/Enter 选择」，引库反倒要为它再包一层玻璃主题 |
| 子串匹配：`includes` + 空格分词 AND（`src/lib/search.ts`） | `fuse.js` | 中文检索没有拼写容错的需求，用户输入的就是完整字词；而 `fuse` 默认给不了 AND 分词，要用还得额外配 |
| 排序：按数据顺序（置顶 + 创建时间倒序） | 按相关度 score 排序 | 结果已被 AND 收窄，当前量级下顺序差异不可感 |
| `?q=` 联动地址栏 | — | 打开带 `q` 的链接自动展开面板并回填，结果链接可分享 |

索引字段：`name` / `desc` / `review` / 一级分类名 / `tags`。结果列表上限 20 条，底部标出命中总数。

#### 已知代价与重新评估的条件

**代价**：不支持缩写模糊命中（`snp` 搜不到 `Snipaste`），且没有相关度排序。

出现下面任一情况即重新评估 —— 但**只考虑引 `fuse.js`，`cmdk` 届时仍无必要**：

- 公开条目超过 300 条，且一次搜索经常命中 10 条以上（排序开始真正影响可用性）；
- 库内英文 / 拼音名称变多，出现「记得大概怎么拼、但打不全」的实际卡壳。

判据落在**真实使用中是否被卡住**，不是条目数本身。`fuse.js` 约 20KB，且要覆盖主题样式 —— 收益不够就不做。

### 3.6 分类模型：从 `Select` 迁到 `Relation`

**这是整个改造中真正的新增工作量，也是修掉「静默丢数据」的前提。**

#### 现状：两套机制错配

| 机制 | 现状 |
| :--- | :--- |
| `分类配置` 数据库（有 `上级`/`子级` 自关联、`IconName`、`Order`、`Enabled`） | 只被用来渲染**一级分类**的图标 / 顺序 / 开关；9 条记录，**层级字段全空** |
| `category1` / `category2`（**Select**） | 实际承担全部归类；`category1` 11 个值、`category2` **35 个值扁平一张表** |
| `导航链接` 里的 `#️⃣ 分类配置`（relation） | **221 条里只填了 1 条** —— 模板给的"正确通道"，基本没用 |

#### 为什么 Select 是错的载体

Notion 的 Select 选项是**属性下拉框里的一张扁平值表**，它与独立数据库的根本差别：

| 能力 | Select 选项 | Relation 记录 |
| :--- | :--- | :--- |
| 挂元数据（图标 / 排序 / 开关 / slug / 说明） | ❌ 只有颜色 | ✅ 任意字段 |
| 表达层级 | ❌ 无父级绑定 | ✅ 自关联 |
| 在独立库里管理（排序 / 计数 / 批量改 / 合并重复） | ❌ 只能在属性弹窗里 | ✅ |
| 约束「二级分类属于哪个一级」 | ❌ 选项全表共享，无法绑定 | ✅ 由父级表达 |
| 改名 | 全表替换，无痕 | 改一条记录 |

**「效率工具出现在 6 个一级分类下」正是第 4 行的直接后果** —— 二级分类的选项列表没有父级绑定，同一个概念被迫在每个一级分类里各登记一次。

#### 更严重的后果：链接会静默消失

`page.tsx` 的白名单机制：

```ts
// src/app/page.tsx:17,26
const enabledCategories = new Set(notionCategories.map(cat => cat.name)); // 来自「分类配置」库
const processedLinks = links.filter(link => enabledCategories.has(link.category1));
```

而 `getCategories()` 查询时带了 `filter: Enabled = true`。于是**两种事实源一旦不一致，链接就被丢弃，且没有任何提示**。实测线上：

| 丢弃原因 | 条数 |
| :--- | :--- |
| `category1` 为空 → 落到 `未分类`，不在白名单 | 14 |
| `数码科技` —— 用插件的 Select 新建了分类值，但「分类配置」里没有对应记录 | 1 |
| `3D打印` —— 「分类配置」里 `Enabled = false` | 13 |
| **合计** | **28（占 221 的 12.7%）** |

**这 28 条在首页上根本不存在，而且你不会收到任何错误。** 也就是说：**你在插件里随手新建一个分类，那个链接就可能永远看不见。**

> ⚠️ **2026-09-12 修订**：原文此处以「`/api/links` 里却都在（`api/links` 不过滤）」作为旁证。`/api/links` 现已加可见性白名单（只返回 `公开`），该旁证失效 —— 复核静默丢弃需直查 Notion，不能再用这个接口。

> ⚠️ **2026-09-12 修订（第 4 步）**：`3D打印` 的 13 条已归档，「分类配置」中该分类记录一并删除；`数码科技` 已在「分类配置」补建并启用（Order=900）。上表只剩「`category1` 为空 14 条」仍待处理 —— 它不是分类缺失，而是条目本身没归类。

> 这是「Select 承载分类」最硬的一条罪证 —— 它把"建分类"变成了一个**不产生元数据的动作**，而系统又要求元数据存在才放行。

#### 迁移做法

1. 在 `分类配置` 中为每个现存的 `category1` 建/补一级记录（补齐 `IconName` / `Order` / `Enabled`）；为每个 `category2` 建二级记录，并用 `上级` 关联到正确的一级。
2. 按 `category1` + `category2` 的现有值，批量把链接的 `#️⃣ 分类配置` relation 写成一/二级记录。
3. 代码侧：`Link` 模型接 relation 得到分类引用（`category1Id` / `category2Id`）；归类缺失的条目落到显式「未分类」并呈现在界面上，替换原先**按分类名做白名单过滤、缺分类即静默丢弃**的做法。
4. **迁移期间保留 `category1` / `category2` 两个 Select 字段**（只读、不删），relation 解析不出时回退读取 —— 可回退。可移除的判据：relation 覆盖全部条目，且新条目在插件里的写入路径已切到 relation；满足后在 Notion 侧删除字段，再清理代码中的回退分支与 `Link` 上的旧字段名（见 `NotionLinkTransitionalProperties` 的说明）。
5. 迁移脚本可基于 `category1`+`category2` 的现有字符串映射，**不需要人工逐条判定**。

> **`Enabled` 的语义**：关闭一个分类 = **该类整体收起** —— 入口不出现在导航里，归入其下的条目也一并**不显示**。
> 「未分类」只承载**没有归类**的条目，不承载「归类了、但那一类被关闭」的条目。两者混同会让关闭分类变成
> 「把条目挤进未分类重新暴露」，等于关闭没生效。因此 `getCategories()` 取**全量**记录（不过滤 `Enabled`），
> 才分得清「被关闭」与「不存在」—— 后者才是归类缺失。

#### 与「捕获」的关系（重要）

**先说结论：插件里选得到 Relation（已实测通过）。** Save to Notion 官方把 relation 列为可填属性（"fill database properties (tags, relation, checkbox…)"），表单里会给出下拉让你选**已有的记录**；字段保持可编辑状态时，选完还能手动调整。

但 Select 与 Relation 在插件里有一个关键差别，而且方向对我们有利：

| 在插件表单里 | `Select`（现在） | `Relation`（改造后） |
| :--- | :--- | :--- |
| 选一个已有的值 | ✅ | ✅ |
| **随手新建一个值** | ✅ ← **正是 bug 的根源** | ❌ 只能选已存在的记录 |
| 挂元数据（图标 / 排序 / 开关 / slug） | ❌ 只有颜色 | ✅ 任意字段 |

`category2` 现在有 35 个扁平值、`效率工具` 跨 6 个一级分类 —— **起因就是插件允许随手新建 Select 值**：这个动作"创建了一个分类"，却不产生任何元数据，而系统又要求元数据存在才放行（后果见 4.1 的 28 条静默丢弃）。**Relation 从源头堵死了这条路** —— 插件里选不到不存在的分类，你只能先在「分类配置」里把它建出来。

**那还要不要用插件的这个能力？—— 不要。**

> **分类本来就该在分诊时填，不该在捕获时填。**

这正好与 3.2 的最小第一步同向：插件只锁 `可见性 = 草稿`，分类留空；攒到周末在 Notion 表格视图里批量填。**分诊决策数不增反减**（一个 `分类` 字段取代两个 Select，从 2 个决策降到 1 个）。

> **已实测（2026-09-12）：插件表单里能选到 relation。** 试验品就是模板自带的 `#️⃣ 分类配置`（→ `分类配置` 库）—— 在 Save to Notion 的 Form 里 `Add New Field` 加上它，确实给出了记录下拉。`合集` 与它同属「relation → 独立库」，结论可直接平移。
>
> 顺带一个反常识的事实：`#️⃣ 分类配置` 221 条里只填了 1 条 —— **不是没这功能，而是插件的 Form 从没配过它**（表单默认只显示自动抓取的 `Name` / `URL` / `icon`，其余属性必须手动 `Add New Field`）。**功能存在 ≠ 功能被用上，中间隔着一个配置动作** —— 这就是本库腐烂的真正入口。

### 3.7 「合集」库的字段设计

**为什么必须是独立库**：`slug` 和 `说明` 存在**合集记录**上（不在链接上），`/c/[slug]` 直接读合集库 —— 见 3.4。用 Select 承载等于把这些元数据寄存在每条链接上，重复且无法一致；而 `slug` 重复就意味着一串分享出去、指向错误页面的短链。

#### 字段

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `名称` | Title | ✅ | 按**朋友的问法**命名：「免费图床」，不是「图床工具集合」 |
| `slug` | rich_text | ✅ | 短链用；规则见下 |
| `说明` | rich_text | —— | 一句话，渲染在分享页标题下方 |
| `封面` | files | —— | 可选；分享页 / OG 卡片用 |
| `排序` | number | —— | 合集列表顺序 + 分享页内条目的稳定顺序 |
| `可见性` | select：公开 / 私人 / 草稿 | ✅ | 默认 `草稿`。**与链接上的 `可见性` 同名同值域**，一套心智模型 |

> 合集库里还会出现一列 `链接`（反向 relation），由 Notion 在建立双向关联时**自动生成**，不需要手建。它看起来"凭空多出来一列"是正常的。

#### `slug` 命名规则（定案）

```text
^[a-z0-9]{2,24}$
```

- **只允许小写英文和数字**：不用中文、不用连字符、不用下划线、不用大写；
- 长度 2–24 字符；
- 优先用**英文短词**，其次全拼：`tuchuang` / `win` / `tools`（命名取向见设计文档 3.3）；
- **必须在合集库内唯一。** Notion 的 rich_text 无法强制唯一约束，所以唯一性由**代码侧构建时校验**：构建期扫描全部 `slug`，发现重复直接失败并报出冲突的两个合集名。

> 为什么唯一性这么要紧：两个合集抢同一个 `slug` 会**静默覆盖**，分享出去的短链指向错误的页面。在分享语境里，这是唯一的「丢面子」级故障 —— 朋友当场看到的是另一个东西，而你不会收到任何提示。同理，校验必须发生在**构建期**，不能等到访客点开。

#### 与链接侧 `合集` 字段的关系

| 位置 | 字段 | 方向 |
| :--- | :--- | :--- |
| `导航链接` 库 | `合集` → relation → 合集库 | 每条链接指向所属合集（**可多选**） |
| 合集库 | `链接` | 自动生成的反向索引（只读） |

一条链接可以同时属于多个合集（「免费图床」里的某个站点，也可以出现在「给朋友的入门包」里）。
与 `Tags` 的分工仍按设计文档 2.1：`Tags` 是对内检索的扁平关键词，`合集` 是对外、可独立分享的策展单位。

> **捕获时同样不要填 `合集`**（插件表单里选得到，但别用）。理由与分类一致，见 3.6：合集是**策展**决策 ——「这条要不要发给朋友看」发生在发布前，不发生在捕获时。每次多一个决策，就是 3.2 要消除的那种摩擦。

## 四、既有缺陷修复

这几项不需要架构改动，可以并行做。

### 4.1 分类白名单会静默丢弃链接

见 3.6 的实测数据（28 条 / 12.7% 在首页不存在，无任何提示）。

**临时缓解**（迁移前的止血）：在 `分类配置` 里为 `数码科技` 补一条记录、给空分类的 14 条补上分类。
**根治**：按 3.6 迁移到 relation，并让兜底逻辑显式呈现「未分类」而不是丢弃。

> 关键点不是"丢了多少条"，而是**丢弃是静默的**。改造后任何"归类缺失"都必须在界面上可见。

### 4.2 ISR 时效：改完 12 小时才看到

```ts
// src/app/page.tsx:6
export const revalidate = 43200;   // 12 小时
```

全仓库 grep 不到 `revalidateTag` / `revalidatePath` / `unstable_cache` / webhook —— **没有任何按需刷新能力**，编辑后只能干等。

> 附带两个坑：`src/lib/notion.ts:21` 的 `REVALIDATE_TIME` 环境变量是**死代码**（Next 只认路由段的 `revalidate` 导出，改它无效）；`cache()` 只在单次请求内去重，不跨请求 —— 真正说话的是 ISR 那一层。

**修法（三层组合）**：

```ts
// ① 安全网：时间兜底，10 分钟
export const revalidate = 600;

// ② 主动触发：给数据打 tag
import { unstable_cache } from 'next/cache';
const getLinks = unstable_cache(fetchLinksImpl, ['links'], { tags: ['links'] });

// ③ 触发入口：src/app/api/revalidate/route.ts
export async function POST(req: NextRequest) {
  if (req.headers.get('x-webhook-secret') !== process.env.WEBHOOK_SECRET)
    return NextResponse.json({}, { status: 401 });
  revalidateTag('links');
  revalidatePath('/');
  return NextResponse.json({ revalidated: true });
}
```

触发方式建议叠加：

- **Notion 原生 Webhook**（已 GA，订阅 `page.created` / `page.properties_updated` / `database.content_updated`）→ 打到 `/api/revalidate`。注意：webhook 只给事件信号，需自己再拉数据；要求公网 HTTPS 端点。
- **兜底**：即使 webhook 挂了，10 分钟的 ISR 也会自愈。

### 4.3 字体链路：国内双重打击

```css
/* src/themes/theme.css:2 */
@import url('https://fonts.googleapis.com/css2?family=Noto+Sans+SC:wght@400;500;700&display=swap');
```

- Google Fonts 在国内基本不可达 / 极慢，且 `@import` 是**串行阻塞**加载；
- `layout.tsx` 还同时走 `next/font/google` 拉 Inter；
- Noto Sans SC 中文字体本身体积巨大。

→ 首屏白字 / 字体闪烁（FOIT）、CSS 阻塞。**对国内访客的首屏体感，这一条杀伤力排前三。**

**修法**：删掉 `@import`，改用系统字体栈：

```css
font-family: -apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei", "Noto Sans SC", sans-serif;
```

国内零下载、零阻塞。要保留品牌字体则用 `next/font/local` 自托管并做汉字子集化。

> ⚠️ **2026-09-12 已修**：`layout.tsx` 去掉 `next/font/google` 的 Inter，`body` 不再挂它生成的 className，字体统一走 `globals.css` 的 `--font-sans`（系统字体栈）。构建不再依赖 Google Fonts。

### 4.4 图标链路

实测线上 221 条的图标来源：

| 图标来源 | 条数 | 占比 | 真实后果 |
| :--- | :--- | :--- | :--- |
| 外部 hotlink（github / framer / gstatic / alicdn…） | 189 | 85.5% | 能用，但**挂在别人服务器上，不牢** |
| **空**（`iconfile` 与 `iconlink` 皆空） | **27** | **12.2%** | **退化为默认地球图标 ← 这才是"难看"的真因** |
| Notion 托管（`prod-files-secure` S3） | 2 | 0.9% | 签名 URL 1 小时过期，但只有 2 条 |

**真正该做的是方案 C**：同步时把图标抓到自有存储（`public/icons/` 或对象存储），落库为固定 URL。**一次顺带解决三件事** —— 27 条空图标（抓 favicon 兜底）、189 条外链不稳定、2 条签名过期。

> 另需补 `referrerPolicy="no-referrer"`（部分站点有防盗链）。

### 4.5 合并已有优化分支

`feature/perf-stage-1-optimization` 已做完：删轮询定时器、lucide 具名导入 + `CategoryIcon.tsx`、`theme.css` 去 Google Fonts、配置读取失败降级。**它是 fast-forward，零冲突，先收下。**

> ⚠️ 合并时 `GEMINI.md` 会冲突（该分支改过此文件，本地已改为指向 `.agents/AGENTS.md` 的软链）。解决方式：**采用软链版本**，内容已迁移进 `.agents/rules/03-代码提交.md`。

### 4.6 必需配置缺失被伪装成「内容为空」

`getCollections` / `getCategories` 在 `NOTION_COLLECTIONS_DB_ID` / `NOTION_CATEGORIES_DB_ID` 缺失时，
**静默返回空数组**。下游无从分辨「配置漏了」与「确实没内容」：线上表现是分享页直接 404、首页分类集体消失，
且没有任何提示。

> ⚠️ **2026-09-27 已修**：改为打日志并置「数据获取失败」标记，分享页与首页据此显示降级提示，
> 不再把配置故障伪装成内容为空。

## 五、改造顺序

```text
0. 合并 feature/perf-stage-1-optimization                    ← 已有成果，先收下
1. 减法：主题收敛到 simple（含改为「跟随系统 + 可手动指定」）、
       小组件全删、去 framer-motion、删轮询定时器、
       修假「最近更新」、删冗余 Navigation                     ← 先做减法
2. pnpm format（全量格式化，单独 style 提交）                  ← 减法后执行，避免格式化待删文件
3. 加 `可见性` 字段 + Save to Notion Form 锁定 `草稿`          ← 最小改动、最大收益
4. 迁移 `力荐👍` → `推荐`，并把继承内容标记 `私人`              ← 见 references/01
5. 分类模型迁移：`category1` + `category2`（Select）→ `分类` relation
       （同时在「分类配置」里补齐层级关系）                     ← 见 3.6
6. 新建「合集」库（字段设计见 3.7）+ `合集` relation + `点评` 字段
7. 迁博客高价值三类（免费图床 / Windows 系统 / 桌面效率工具）
8. 搜索（Cmd+K）+ 分享页 `/c/[slug]`
9. 修既有缺陷：字体本地化、ISR 降频 + revalidateTag、图标链路、
       分类白名单静默丢弃（4.1）
```

**为什么第 3 步排这么前**：它同时解决「维护不及时」和「整理成本高」，且改动只有三个小动作。

**为什么第 5 步在第 6 步之前**：`合集` 是策展层，`分类` 是结构层；先把结构层的承载方式换对，再往上加策展层，否则两次都要动同一批数据。

**为什么格式化排在第 2 步**：减法是删除，格式化的对象应该是留下的文件 —— 顺序反了会让减法的 diff 难以阅读。
