# 分类图标方案

> 本文档回答**一级分类的图标从哪来、怎么配、怎么渲染**。定案日期 2026-09-14。
>
> 数据模型见 [`01-产品定位与架构设计.md`](./01-产品定位与架构设计.md)；界面语言见 [`03-界面设计.md`](./03-界面设计.md)。
>
> ⚠️ **本文不涉及站点图标。** 每条链接的 favicon（`Link.icon`：外链 / 空 / Notion 签名 URL）是另一条链路，见 [`02-改造路线.md`](./02-改造路线.md) 4.4。两者唯一的共同点是都叫「图标」。

---

## 一、问题

`IconName` 是 Notion `分类配置` 库中的 **rich_text 自由文本**字段 —— 没有枚举约束、没有候选项、没有填写提示。

渲染侧则由 `CategoryIcon.tsx` 持有一张 57 项的硬编码白名单：

```tsx
const IconComponent = ICON_MAP[name] || FallbackIcon; // 查不到 → 静默退化为 Globe
```

两侧互不知情，于是**失败是静默的**：白名单外的名字不报错、不警告、不提示，直接显示成地球。

实测（2026-09-14）线上 10 个一级分类，**其中 5 个填的是真实存在的 lucide 图标名，却因不在白名单里而退化**：

| 分类 | `IconName` | 渲染结果 |
| :--- | :--- | :--- |
| 信息源 | `Book` | 🌍 |
| AI大模型 | `Brain` | 🌍 |
| 文字处理 | `LetterText` | 🌍 |
| 知识管理 | `BookOpenText` | 🌍 |
| 桌面软件 | `MonitorDot` | 🌍 |
| 其他 | （空） | 🌍 |

这些名字在 lucide 里全部真实存在。**出问题的是机制，不是数据。**

---

## 二、定案：解析移到服务端

把「把名字翻译成图形」这件事，从**构建期**挪到**运行期**、从**客户端**挪到**服务端**。

```text
Notion IconName（自由文本）
      │
      │  服务端：getCategories() 读取分类后解析
      ▼
 resolveCategoryIcon()  ──►  CategoryIconData | null
      │                       （判别联合，普通对象，可跨 RSC 边界）
      ▼
 <CategoryIcon>   纯渲染器：不查表、不识别图标名
```

四项收益：

| 收益 | 说明 |
| :--- | :--- |
| **覆盖面 57 → 5230** | 改用 lucide 全量导出（含全部历史别名），其中 5229 个可渲染 |
| **客户端不再持有图标库** | 57 项静态导入整体删除，只留一个兜底图标 |
| **首屏零延迟** | SSR 直出，无异步加载、无闪帧 |
| **构建产物不膨胀** | 不产生 per-icon chunk（这是懒加载方案的主要代价） |

## 三、`IconName` 的三种取值

| 取值形态 | 判据 | 解析结果 | 渲染方式 |
| :--- | :--- | :--- | :--- |
| 空 / 未填 | 空字符串 | `null` | UI 兜底（`Globe`） |
| 纯 ASCII | `/^[\x00-\x7F]*$/` | `{ kind: 'svg', inner }` | 套 `<svg>` 外壳注入 |
| 含非 ASCII | 上者取反 | `{ kind: 'text', value }` | React 文本节点 |

**判据为什么是「非 ASCII」而不是「是 emoji」**：lucide 的图标名全部由 ASCII 字符构成，「含非 ASCII」不可能误伤图标名；同时它比 `\p{Extended_Pictographic}` 更宽，顺带覆盖 `→ ★ ✓` 这类符号。代价是填中文（如「书籍」）也会被当文本渲染 —— 但这不比静默给一个地球更差。

### 3.1 命名兼容

解析器**两级查找**：先按原样匹配，再按 `kebab → PascalCase` 转换后匹配。

这样 Notion 侧既可以直接照抄 [lucide.dev](https://lucide.dev/icons) 上的名字（官网用 kebab），也可以填 React 用法里的 PascalCase：

| Notion 里填 | 命中路径 |
| :--- | :--- |
| `book-open-text` | kebab → `BookOpenText` |
| `BookOpenText` | 原样 |
| `circle-play` | kebab → `CirclePlay` |
| `PlayCircle` | 原样（历史别名，仍在全量导出中） |

> **转换方向不可反。** `PascalCase → kebab` 不可靠：`PlayCircle` 的官网名是 `circle-play`、`BarChart` 是 `chart-bar`、裸 `Layout` 已不存在。
>
> 实测：`dynamicIconImports` 的 1544 个 kebab 名经机械转换后，**1544 / 1544 全部命中**全量导出。

## 四、实现要点

一条数据流、四个环节。本节只固定**职责、形态与约束**，具体写法见代码；完整改动清单见第五节。

### 4.1 数据形态（`src/types/notion/category.ts`）

`Category` 增加一个字段承载解析结果：

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `iconName` | `string` | Notion `IconName` 原始值。保留用于溯源与对账，UI 不直接渲染它 |
| `icon` | `CategoryIconData \| null` | 解析结果。`null` = 无图标或名字认不出，由 UI 兜底 |

`CategoryIconData` 是判别联合，两种形态对应两条渲染路径：

```text
CategoryIconData =
  | { kind: 'svg',  inner: string }    // lucide 图标：<svg> 内部标记
  | { kind: 'text', value: string }    // emoji / 符号：作为文本渲染
```

> 类型必须落在 `types/` 层。客户端渲染器要引用它，而解析器所在模块（`src/lib/icon-svg.ts`）全量导入 lucide ——
> 若从那里引用，一旦有人把 `import type` 误写成值导入，整个图标库会被拖进浏览器产物。放 `types/` 层可以杜绝这个可能。

### 4.2 解析器（新增 `src/lib/icon-svg.ts`，**仅服务端引用**）

```text
resolveCategoryIcon(name) -> CategoryIconData | null

  key ← name.trim()
  key 为空               → null
  key 含非 ASCII         → { kind: 'text', value: key }
  key 命中 lucide 导出   → { kind: 'svg', inner: 由图形数据拼出的标记 }
  以上都不是             → null  +  服务端 warn

  「命中」= 两级查找：先按原样，再按 kebab → PascalCase 转换后
```

四条实现约束 —— 都是实测踩出来的，不是推测：

| 约束 | 为什么 |
| :--- | :--- |
| **不得使用 `react-dom/server`** | App Router 会把路由文件的依赖链编进客户端图，而 Next 禁止这条链上出现 `react-dom/server` —— 引入 `renderToStaticMarkup` 会让构建直接失败。改为从 lucide 组件的 forwardRef `render` 取出图形数据、自行拼串 |
| 取导出属性必须用 `Object.hasOwn` 挡一道 | `IconName` 是自由文本，`__proto__` / `constructor` / `toString` 会命中原型链，可能把原型对象当成图标组件 |
| 取到的值必须校验「确实是图标组件」 | lucide 另外导出 `createLucideIcon`（函数）与 `icons`（数据对象）两个非组件成员。判据用 `$$typeof === Symbol.for('react.forward_ref')` —— 正向判据比硬编码排除名单耐升级 |
| 文件顶部必须标注「仅服务端引用」 | 它导入 lucide 全集，被客户端组件直接 import 会把整包拖进浏览器产物 |

> **图形数据怎么取。** lucide 把图标数据闭包在组件内部、不对外暴露，但它的组件是 forwardRef 对象，
> 其 `render` 会把 `iconNode`（`[元素名, 属性表][]`）透传给内部元素 —— 取出来自行拼串，全程不经 React 渲染。
> 实测 5230 个图标组件里 **5229 个**能取出（唯一取不到的是通用组件 `Icon`，本就该排除）；
> 属性名全是 SVG 原生名（`d` / `cx` / `points`…），无需改写，只需滤掉 React 的 `key`。

### 4.3 渲染器（重写 `src/components/ui/CategoryIcon.tsx`）

从「查表组件」瘦成**纯渲染器** —— 不查表、不识别图标名，只按 `icon` 的形态分派：

```text
CategoryIcon({ icon, className })

  icon 为 null        → <Globe />                         兜底
  icon.kind = 'text'  → <span>{icon.value}</span>          React 文本节点，自动转义
  icon.kind = 'svg'   → <svg> + dangerouslySetInnerHTML    注入静态标记
```

- 那 57 项 `ICON_MAP` 与其余具名导入一并删除，客户端只保留一个兜底图标。
- `text` 形态的 emoji 字形小于同尺寸线条图标，放大一档（约 `1.15em`）后在视觉上对齐。

> **`dangerouslySetInnerHTML` 的边界必须写进代码注释。** 注入内容是 lucide 在服务端渲染出的静态标记；用户输入仅作查表 key，查不到即 `null` —— **不存在外部字符串拼入 HTML 的路径**。`text` 形态走 React 文本节点，天然转义。不注释的话，后来者会把它误判为注入风险。

### 4.4 数据层接入（`src/lib/notion.ts`）

`getCategories()` 在排序前补一道 `iconName → icon` 的解析，其余函数不动。

不在 `toCategory()` 里做：那是 `src/types/` 下的纯转换层，不应依赖渲染库。

`getCategories()` 读的是**全量**分类（含二级）。二级记录当前 `IconName` 全为空，在解析器首行即返回 `null`，无额外开销。

## 六、代价与边界

1. **服务端 bundle 增加约 5MB**（lucide 的 cjs 产物 4.9M）。项目是 ISR、`revalidate = 600`（10 分钟，见 `src/app/page.tsx`），不是每请求执行；实测服务端全量 `require` 耗时 **27ms**。
2. **用到 `dangerouslySetInnerHTML`。** 注入内容来自 lucide 包的静态渲染结果，用户输入只作查表 key、查不到即 `null` —— **不存在外部字符串拼入 HTML 的路径**。该边界已写入代码注释，避免后来者误判为注入风险。
3. **图标改动生效跟随 `revalidate` 周期，当前 10 分钟。** 图标与分类数据同批产出，改 Notion 后最多等一个缓存周期可见。若要秒级可见，需额外接入 `revalidateTag`。
4. **图标名写错只在服务端日志 `warn`。** 这是改进（从静默变为可见，构建期即可发现），但前提是有人看构建 / 运行日志。
5. **emoji 不跟随主题色。** 侧栏区块标题的容器带 `text-primary`，线条图标会继承该色，emoji 恒为彩色。这是 `03-界面设计.md`「线条图标 + 主题色」之外的局部例外，属本方案的已知取舍。
6. **客户端动态场景不适用。** 若将来需要实时预览或"用户自选图标"这类运行期在浏览器里换图标的功能，本方案走不通，需另开接口。

## 七、排除的方案

| 方案 | 结论 | 原因 |
| :--- | :--- | :--- |
| 扩充 `ICON_MAP` 白名单 | 排除 | 仍是构建期常量。Notion 侧填白名单外的名字照样静默退化，只是把墙挪远了几米 |
| `dynamicIconImports` 客户端懒加载 | 排除 | 0.468 无 `DynamicIcon` 组件，需自写 `React.lazy`；1544 个图标各切一个 chunk，构建产物膨胀；白名单外的图标首屏会闪一帧 |
| 客户端全量导入 lucide | 排除 | 1000+ 图标进浏览器产物 |
| 图标数据全量内联 | 排除 | 1544 个 `iconNode` 实测 313KB / gzip 65KB，为 10 个图标不划算 |
| Iconify 作为图标源 | 排除 | 同为运行期解析，相对本方案的唯一增量是「跨库混用」；而其 lucide 集仅 1544 个，**覆盖面反而小于本方案的 5230**，等于白添一个外部依赖 |
| Notion 原生 `page.icon` | 排除 | 图标集覆盖不全：26 个常见语义词实测缺 6 个，恰含 `Palette` / `Film` / `Cpu` / `Monitor`；资源端点非官方承诺，且对 Node `fetch` 一律 403（仅部分客户端可访问） |
| 统一改用 emoji | 排除 | 与 `03-界面设计.md` 的线条语言冲突。但作为**可选路径**并入三态语义，而非封死 |

## 八、Notion 侧填写规范

`IconName` 为自由文本，按以下优先级填写：

| 想要的效果 | 怎么填 | 例 |
| :--- | :--- | :--- |
| 线条图标（推荐） | 从 [lucide.dev](https://lucide.dev/icons) 找到图标，复制它的名字。<br>kebab 与 PascalCase 均可 | `book-open-text` 或 `BookOpenText` |
| 彩色 emoji | 直接输入 emoji | `📚` `🧠` `⚙️` |
| 不要图标 | 留空 | — |

**不推荐**：中文词（如「书籍」）会被当文本渲染，能显示但排版效果取决于字体与尺寸。

**名字写错**：不会崩，但会退化。服务端日志中会出现 `[icon] 无法识别的图标名「xxx」`，据此定位。
